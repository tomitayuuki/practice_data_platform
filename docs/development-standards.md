# 開発標準

## 概要
本書は、本データ基盤の開発において準拠すべきルールを定義する。対象は「命名規則」「レイヤー処理範囲」「データ品質基準」「Git規約」「作業単位ドキュメントの様式」「Python実行環境」の6つ。

本書は「どう実現するか」のうち、内容に依存する**パターン・ルール**を扱う。固定のファイル配置は`docs/repository-structure.md`、Snowflake上の具体的なDB・スキーマ構成などのインフラ設計は`アーキテクチャ設計書`（`docs/backlog.md` 015番）で定める。

## 1. 命名規則
基本方針は、名前だけで「何者か」がある程度分かるようにすること。dbtのコミュニティ標準の規約を基本とし、独自ルールは設けない。全体を通してスネークケース（`_`区切り）で統一する。

### 1.1 model
| レイヤー | 命名パターン | 例 |
|---|---|---|
| staging | `stg_<ソース名>__<エンティティ名>` | `stg_moneyforward__transactions` |
| intermediate | `int_<エンティティ名>__<変換内容>` | （現状未使用） |
| marts | `mart_<エンティティ名>` | `mart_transactions` |

- ソース名とエンティティ名の区切りはアンダースコア2つ（`__`）とする。
- martsはファクト／ディメンションを分けず、分析用に整形した1本のテーブルとして`mart_`接頭辞で統一する。マネーフォワードにはカテゴリのマスタが別ファイルとして存在せず、独立したディメンションを持つ実体がないため。

### 1.2 source
`sources.yml`では「システム名＋データ名」で定義する。

- source名：取得元のシステム名（例：`moneyforward`）
- table名：そのシステム内のデータ単位（例：`transactions`）

### 1.3 seed
- ファイル名（＝テーブル名）はスネークケース・複数形とする（例：`category_mappings.csv`）。

### 1.4 column
| 種別 | ルール | 例 |
|---|---|---|
| 主キー・外部キー | `<エンティティ名>_id` | `transaction_id` |
| 日時 | タイムスタンプは`_at`、日付のみは`_date` | `transaction_date` |
| 真偽値 | `is_`または`has_`接頭辞 | `is_refund` |
| 金額 | `_amount`接尾辞（金額を単独で持つ場合は`amount`） | `refund_amount` |

- 取得元のファイル・システムの列名が日本語等、英語のスネークケースでない場合は、**値はそのまま、列名だけを英語のスネークケースに変換して取り込む**（取り込み処理のマッピングで対応し、元ファイル自体は編集しない）。具体的な対応表は、各取得元を取り込む作業単位の基本設計書に記載する（マネーフォワードの例：`.steering/20261003-ingestion-pipeline/design.md`）
- 列名を変換した場合は、dbtの`sources.yml`における該当列の`description`に、元の列名（例：「元のCSVでは`計算対象`」）を記載し、dbt docs上でも変換前の列名を辿れるようにする

### 1.5 macro
- 特にルールは設けない。処理内容が分かる名前にする。

### 1.6 test（`tests/`配下のカスタムテスト）
- `assert_<検証内容>`とする（例：`assert_no_duplicate_transactions`）。
- 「違反しているデータを返すクエリ」を書き、0行ならパスとなるdbtのシングルテストの仕組みに沿い、「〜であることを検証する」意味で`assert_`を用いる。

### 1.7 dbt外
- `ingestion/`のスクリプトおよび`sample_data/`のファイルには、現状ルールを設けない。内容が分かる名前にする。

### 1.8 スキーマ
- dbtのカスタムスキーマ機能を用い、モデルのレイヤー（staging／intermediate／marts）ごとにスキーマを分ける。
- 実際に作成するDB・スキーマの構成（環境の分離、生データ用DBの有無など）は`アーキテクチャ設計書`で定める。
- ソースシステムを跨いだスキーマ分割は、現状ソースがマネーフォワードのみのため設けない。

### 1.9 ファイル取り込み時のクラウドストレージ（S3等）配置
- フォルダ階層は、**環境／取得元システム／データの種類**の順とする。Snowflakeのデータベース（環境）／スキーマ（システム）／テーブル（データの種類）という階層とそのまま対応させる（例：`s3://.../prod/moneyforward/transactions/` ↔ `RAW_PROD.MONEYFORWARD.TRANSACTIONS`）。
- データの種類（最下層）の配下は、`inbox/`（未取り込み）と`archive/`（取り込み済み）に分ける。外部ステージは`inbox/`のみを参照し、取り込みが成功したファイルは`archive/`へ移動する。
- 取り込み処理が途中で失敗した場合は、アップロード済みのファイルを`inbox/`から削除する（成功時の`archive/`移動と対になる、失敗時の後始末）。`inbox/`に未処理ファイルを残したままにすると、次回実行時に複数ファイルが同時に読み込まれ、`MERGE`等の重複排除ロジックの前提が崩れる可能性がある。
- IAMロール・ポリシーによるアクセス制御は環境単位までとし、取得元システム・データの種類単位では分割しない（`.steering/20261003-ingestion-pipeline/design.md`で比較検討済み。将来、特に機密度の高いデータが登場した場合は個別に再検討する）。

## 2. レイヤー処理範囲
| レイヤー | 役割 | 方針 |
|---|---|---|
| staging | 最低限のデータクレンジングのみを行う。ビジネスロジックは含めない | ソース1テーブルにつき1モデル（1:1） |
| intermediate | 中間加工層。分析前のデータの組み合わせを作る | 複数媒体を横断する必要が出るまでは作成しない |
| marts | 分析・可視化に使う層。分析したい形に整形したテーブルを作る | 月次×カテゴリ別といった細かい集計・グルーピングはBIツール側で行う |

## 3. データ品質基準
`docs/requirements.md`のデータ品質要件を、以下のルールで技術的に担保する。

### 3.1 重複排除
- マネーフォワードのCSVに含まれる`ID`列を取引の一意キーとし、stagingで`transaction_id`にリネームして用いる。
- source（Snowflake上のrawテーブル）の時点で、`ID`による重複を排除した状態で保持する。同一期間のCSVを再取り込みしても重複しないようにする。
- 完全な生データの履歴はS3の生ファイルで保持するため、source側で全取り込み分を積み上げる必要はない。
- 重複排除の具体的な実装方法（取り込み時のMERGEなど）は、実装時の設計（アーキテクチャ設計書、各作業単位の`design.md`）で定める。
- `MERGE`で重複排除を実装する場合、`WHEN NOT MATCHED THEN INSERT`は**ターゲット側に既にある行との重複しか防げず、ソース側（一時テーブル）内の重複はそのままINSERTされる**点に注意する。一時テーブルの中身は必ず`QUALIFY ROW_NUMBER() OVER (PARTITION BY <一意キー> ORDER BY ...) = 1`等で一意化してから`MERGE`する（`.steering/20261003-ingestion-pipeline`で実際に発生・修正した不具合）。

### 3.2 テスト
- 主キー・外部キーには`not_null`と`unique`のテストを必須とする。複合キーの場合は、複合の範囲でテストする。
- sourceの`ID`列（`transaction_id`）にも`sources.yml`上で同テストを設定し、取り込み処理の不備で重複が混入した場合に検知できるようにする。
- テストは原則`schema.yml`に定義する。`schema.yml`に書けない独自のロジックのみ`tests/`配下のシングルテストとする。

### 3.3 テスト失敗時の扱い
- 重要度は`error`とし、処理を止める。`warn`は使用しない。

## 4. Git規約

### 4.1 ブランチ運用
- `main`と`feature`ブランチの構成とする。
- 作業単位ごとに`feature/[YYYYMMDD]-[開発タイトル]`を作成する。`.steering/[YYYYMMDD]-[開発タイトル]/`と1対1で対応させる。
- 基本設計をフェーズに分割した場合（CLAUDE.mdの「作成するドキュメント（作業単位）」）は、フェーズごとに`feature/[YYYYMMDD]-[開発タイトル]-phase[番号]`を作成し、`.steering/`配下のフェーズのフォルダと1対1で対応させる。要件定義書は最初のフェーズのPRに含め、以降のフェーズで要件定義書を修正した場合はそのフェーズのPRに含める。
- `main`は、完了・承認済みの状態のみを保つ。
- `main`にはブランチ保護ルールを設定し、後述のCIチェック（4.3）を通過しない限りマージできないようにする。featureブランチへのpush自体は制限しない。

### 4.2 コミットメッセージ
- Conventional Commits形式とし、`<種類>: <日本語の要約>`の形で記載する（例：`feat: マネーフォワードのstagingモデルを追加`）。
- 種類は以下を用いる。

| 種類 | 用途 |
|---|---|
| `feat` | 機能追加（モデル・スクリプトの追加など） |
| `fix` | 不具合修正 |
| `docs` | ドキュメントの変更（`docs/`、`.steering/`など） |
| `refactor` | 挙動を変えない整理 |
| `test` | テストの追加・修正 |
| `chore` | 上記以外の雑務（設定ファイルの変更など） |

### 4.3 CIによる自動コードレビュー
- featureブランチから`main`へのPR（プルリクエスト）を作成すると、GitHub Actionsが自動でコードレビューを実行する。
- PRに追加でpushするたびに、CIは自動で再実行される。
- レビューで指摘があった場合は、同じfeatureブランチに修正をpushする（新しいPRは作らない）。
- CIのチェックが通るまで、`main`へはマージできない（4.1のブランチ保護ルールによる）。
- **既知の例外**：CIワークフロー自体（`.github/workflows/claude-review.yml`）を変更するPRは、セキュリティ対策（PR上のワークフロー内容が`main`と不一致の場合の自己スキップ）により自動レビューが機能しない。該当するPRは、ブランチ保護のBypass機能を使い、人が手動確認の上でマージする（詳細は`.steering/20260929-github-actions-ci/design.md`）。

#### 4.3.1 レビューの役割分担
- ユーザー（依頼者）は、CLAUDE.md開発フローのステップ7で「要件定義書のやりたいことが実現できているか」を確認する。
- それ以外の技術的な確認（正しさ、設計との整合、テスト、規約等）は、CIレビューが担う。レビューの速度・必要な知識量・細部の網羅性ではAIが有利であり、依頼者の意図を正確に知っているのは依頼者のみであるため。
- CIレビューの観点と判定基準は本節を正とし、CIワークフローの指示は本節を参照する形とする（観点を見直す際にワークフローを変更せずに済むようにするため）。

#### 4.3.2 レビュー観点
CIレビューは、PRの差分と、差分に関連するファイル（設計書・YAML・テストケース一覧・永続ドキュメント等）を対象に、以下の観点で確認する。レビュー結果のコメントには、観点ごとに「問題なし」「指摘あり」「該当なし」のいずれかを明記する。

| # | 観点 | 確認内容 |
|---|---|---|
| 1 | 正しさ | ロジックのバグ、境界値・例外ケース（NULL・重複・0件・符号等）、SQL特有の落とし穴（JOINによる行の増加、`MERGE`のソース側の重複等） |
| 2 | 設計との整合 | 実装が、承認された基本設計書・YAML（テーブル定義）のとおりになっているか |
| 3 | テストの妥当性 | テストケース一覧の各ケースに対応するテストがあるか、テストが誤りを検出できる内容か、実施結果が記録されているか |
| 4 | セキュリティ・データ取扱い | 秘密情報・実データの混入が無いか、権限が最小限か、publicリポジトリで公開されて問題のある情報が無いか（`CLAUDE.md`のデータ取扱いの原則、`docs/architecture.md`のアカウントセキュリティ） |
| 5 | 環境分離 | DEV／PRODを跨いだ参照・書き込みが無いか（`docs/architecture.md`の環境分離） |
| 6 | 本番への影響・リリース | 本番環境で取り返しのつかない操作が無いか、リリース手順書が成果物とかみ合っているか、失敗時に戻せるか |
| 7 | 規約の遵守 | 本書（命名規則・レイヤー処理範囲・Git規約・作業単位ドキュメントの様式等）に沿っているか |
| 8 | ドキュメントの整合 | 永続ドキュメントの更新漏れ、ドキュメント間の矛盾、存在しない節・ファイルへの参照が無いか |
| 9 | 再実行の安全性・運用 | 同じ処理を再実行しても壊れないか、失敗時に後始末されるか |
| 10 | 性能・コスト | 不要に重い処理や、予算（`docs/requirements.md`の月額目安）を圧迫する設定が無いか |
| 11 | 保守性 | 読みやすさ、重複、判断の理由のコメント、過剰な複雑さ |

#### 4.3.3 判定基準
| 判定 | 基準 | 主に該当する観点 |
|---|---|---|
| FAIL | そのままマージ・リリースすると実害が出る指摘（集計結果の誤り、データの重複・欠落、秘密情報・実データの混入、環境を跨いだ参照・書き込み、取り返しのつかない本番操作、リリース手順書と成果物の食い違い等） | 1・4・5・6 |
| FAIL | 開発フローの前提が崩れる指摘（承認された設計と実装の食い違い、テストケースに対応するテストが無い・未実施等） | 2・3 |
| PASS（指摘のみ） | 直すことが望ましいが実害は無い指摘 | 7〜11 |

- 7〜11の観点でも、程度が著しいもの（ドキュメントの矛盾により以降の作業の判断を誤るおそれがあるもの、明らかに予算を超えるコスト設定等）はFAILとしてよい。

### 4.4 mainへの取り込み
- featureブランチは、GitHub上のPR画面から「Squash and merge」でmainに取り込む。作業単位ごとに1コミットとなる。
- squash時のコミットメッセージも、Conventional Commits形式で作業単位全体を表す1行とする。
- マージ後、featureブランチは削除する。作業の経緯は`.steering/`配下のドキュメントに残す。

### 4.5 CDによるdbtのリリース
PROD環境へのdbtのリリースは、GitHub ActionsのCD（`.github/workflows/dbt-release.yml`）で行う。手作業での`dbt run`／`dbt build --target prod`は行わない。仕組みの詳細は`.steering/20261012-dbt-cd/design.md`、接続に使うユーザーは`docs/architecture.md`の「ロール・権限設計」を参照。

#### 4.5.1 承認の役割
| 承認 | タイミング | 判断すること | 操作 |
|---|---|---|---|
| マージの承認 | CLAUDE.md開発フローのステップ7 | 要件定義書のやりたいことが実現できているか | ユーザーがClaudeにマージを指示する |
| リリースの承認 | CDの承認待ち | 今、本番に反映してよいか | ユーザーがGitHubの画面で承認する |

#### 4.5.2 リリースの契機
- **マージ時**：`main`へのマージのうち、`dbt/`配下・`requirements.txt`・`.github/workflows/dbt-release.yml`のいずれかに変更があるものは、CDが自動で起動し、承認待ちになる。それ以外（ドキュメントのみ等）のマージでは起動しない
- **手動実行**：新しいデータを`RAW_PROD`に取り込んだ後など、資材の変更が無くても作り直したい場合は、ユーザーが手動実行する。staging（view）は取り込んだ時点で新しいデータが見えるが、mart（table）は作り直すまで反映されない

#### 4.5.3 手順
**マージで起動した場合**
1. 承認待ちになると、GitHubからユーザーにメールが届く
2. GitHubの「Actions」タブで「dbt Release (PROD)」の承認待ちの実行を開き、「Review deployments」を押す
3. 契機（どのマージか）を確認し、`prod`にチェックを入れて「Approve and deploy」を押す（今は反映したくない場合は「Reject」）
4. 実行が成功（緑のチェック）で終わったことを確認する

**手動実行する場合（新しいデータの取り込み後の作り直し等）**
1. 取り込みスクリプトで`RAW_PROD`にデータを取り込む
2. 「Actions」タブ →「dbt Release (PROD)」→「Run workflow」を押し、「Use workflow from」が`main`であることを確認して「Run workflow」を押す（`main`以外のブランチはEnvironment `prod`の設定により拒否される）
3. 起動した実行を開き、上記の2〜4と同じく承認して結果を確認する

- リリースは同時に1つだけ動く。承認待ち・実行中の実行がある間に次の実行が起動した場合、次の実行はその後ろで待つ（後ろで待つのは常に最新の1件）。先の承認待ちを承認すると、その後に最新の実行が承認待ちになる。先の承認待ちが不要な場合は却下してよい。承認後に実行中のリリースは途中で止まらない
- 承認待ちは、承認・却下しない限り30日で自動的に取り消される
- 成功時はメールは届かない。結果は「Actions」タブで確認する

#### 4.5.4 失敗した場合の対応
- 失敗すると、GitHubからユーザーにメールが届く。「Actions」タブで、失敗した実行の`dbt build`のステップのログを確認する
- `dbt build`は、テストが失敗した箇所より下流のモデルを作り直さない。上流（source・staging）のテストの失敗であれば、martは前回の状態のまま残る。martを作り直した後に分かった異常（martのテストの失敗、ロジックの誤り等）は、自動では元に戻らない
- 原因がデータ（取り込んだデータの重複等）の場合は、データを直してから手動実行でリリースし直す。原因がモデルの場合は、修正したPRをマージしてリリースし直す。直ちに前の状態に戻したい場合は、原因のPRをrevertするPRをマージしてリリースする
- 接続エラー（認証の失敗等）の場合は、`SVC_DBT_PROD`の公開鍵とEnvironment `prod`のSecretsの設定を確認する
- ログをClaudeに共有する前に、取引の内容が含まれていないかを確認し、含まれる場合は伏せる（通常、dbtのログに出るのはモデル名・テスト名・件数のみ）

#### 4.5.5 受け入れテストの記録
- dbtのリリースのみの作業（リリース手順書を作らない作業）では、受け入れテストの結果を要件定義書の「受け入れテストの結果」の章に記録する（5.1）
- リリース後に記録し、別のPRで`main`に取り込む（CLAUDE.md開発フローのステップ9）

## 5. 作業単位ドキュメントの様式
CLAUDE.mdの「作成するドキュメント（作業単位）」で定める各ドキュメントの章立てと記載ルールを定める。各ドキュメントの目的・作成者・承認の要否はCLAUDE.mdを参照。

### 5.1 要件定義書
依頼者の要望を、依頼者の言葉で、依頼者が理解できる抽象度で書く。「どう実現するか」は書かない。要件をどう確認するかの具体化は、テストケース一覧（5.3）で行う。

| 章 | 内容 |
|---|---|
| 目的 | 何のために、何をしたいか |
| スコープ | 対象（やること）と対象外（やらないこと） |
| 要件 | やりたいことを項目に分けて書く |
| 依頼者が指定する条件 | 依頼者から「こう実現してほしい」と指定する条件 |
| 前提情報 | ヒアリング等で得た、依頼者しか知らない情報（データの仕様等） |
| 完了条件 | 依頼者が「やりたいことができた」と判断する基準 |

- 作業者側の都合（開発・セキュリティ上の理由等）で決まる条件は、要件定義書ではなく基本設計書に書く。
- 前提情報のうちデータの仕様は、実装時に永続側（列単位はdbtの`sources.yml`、IF単位は`docs/interfaces.md`）へ転記し、転記後は永続側を正とする。実装タスク一覧に転記のタスクを含める。
- 完了条件は、受け入れテスト（5.6）で依頼者が確認する内容と対応させる。
- リリース手順書を作らない作業（dbtのリリースのみの作業等）では、リリース後に末尾へ「受け入れテストの結果」の章を追加し、完了条件ごとに確認方法・結果・確認日を記録する（4.5.5）。リリース手順書を作る作業では、受け入れテストはリリース手順書で行う（5.6）。

### 5.2 基本設計書
要件定義書の「何をしたいか」を「どう実現するか」に落とす。「設計内容」までは、依頼者が要件を満たせるかを判断できるように書く。

| 章 | 内容 |
|---|---|
| 概要 | どう実現するかの全体像（図があると望ましい） |
| 開発の分割 | フェーズに分割するかどうか。分割する場合は各フェーズの範囲（分割しない場合はその旨のみ） |
| 設計内容 | 処理の流れ、作るもの、データの持ち方等 |
| テーブル定義 | dbtを用いる場合は、YAML（`sources.yml`／`schema.yml`）の参照先のみを書く |
| 設計判断とその根拠 | 技術的な選択とその理由、検討した他の選択肢 |
| 永続ドキュメントへの反映 | 基盤全体に影響する判断のうち、どの永続ドキュメントに何を反映するか |

- dbtを用いる場合、テーブル定義はYAMLを正とし、基本設計書には重複して書かない。YAMLは基本設計書と同時に作成し、セットでレビュー・承認を得る。この時点のYAMLは列定義と`description`までとし、テストの定義はテストケース一覧の承認後に追加する（5.4）。
- 基本設計の検討で依頼者の想定と異なることが分かった場合は、依頼者に確認の上で要件定義書を修正する。

### 5.3 テストケース一覧
作業者が実施するテストの計画と結果を、以下の列を持つ表形式（Markdown）で作成する。dbtを用いるかどうかに関わらず共通とする。

| No. | テスト区分 | 対象要件 | 確認内容 | 期待結果 | 対応テスト名（任意） | 実施結果 | 実施日 |
|---|---|---|---|---|---|---|---|

- テスト区分：以下のいずれかを記載する

| テスト区分 | 対応する工程 | 確認すること |
|---|---|---|
| 単体 | 詳細設計（実装資産） | 部品（モデル・ロジック等）が1つずつ正しく動くか |
| 結合 | 基本設計 | 部品を組み合わせて、基本設計どおりに動くか |
| 総合 | 要件定義 | 要件定義書のとおりに、全体として実現できているか |

- 対象要件：要件定義書・基本設計書のどの要件に対応するかを記載する
- 確認内容：何を、どう確認するかを記載する
- 期待結果：正常に満たされていれば得られるはずの結果を記載する
- 対応テスト名：実装時にテストを自動化した場合（dbtの`schema.yml`のテスト名等）に記載する。手動確認のみの場合は空欄でよい
- 実施結果：PASS／FAILを記載する。FAILの場合は原因と対応も書く
- 実施日：テストを実施した日付

- 行は対象要件の順に並べる（要件とテストケースの対応を追いやすくするため）。
- 依頼者による受け入れテストは、テストケース一覧には含めない（5.6）。
- 表の列だけでは残しきれない確認手順・実際の値・後始末等の詳細は、テストケース一覧の末尾に「実施結果の補足」の節を設けて自由記述で残す。

### 5.4 テストケース一覧とYAMLの対応（dbtを用いる開発）
CLAUDE.mdの「テストケース一覧」は、dbtを用いる開発でも省略せず作成する（dbtだから別扱いにはしない）。5.3の様式を前提に、dbt固有の扱いは以下のとおり。

- テストケース一覧は基本設計書（YAMLを含む）の承認後、実装前に作成する。この時点のYAMLにはテストがまだ定義されていないため、「どの要件を」「どう確認するか（例：取引IDの一意性を確認する）」「期待結果」を日本語で記載する。dbtの標準テスト（`not_null`/`unique`/`relationships`等）、unit test、または3.2の`tests/`配下のシングルテストで実現できる想定であることが分かる形にする。
- 実装（CLAUDE.md開発フローのステップ3）でYAMLにテストを定義する際、テストケース一覧の各ケースと対応するテストが分かるよう、テストケース一覧側に対応するテスト名を追記する。
- テストの実施は`dbt test`コマンドで行う。実施結果（PASS/FAIL）は、テストケース一覧の該当行に追記する。
- 3.2・3.3のデータ品質基準に関するテストルールは、テストケース一覧の一部として扱う。

### 5.5 実装タスク一覧
- チェックボックス付きの階層リストで作成する。
- ユーザーが実施するタスクは「（ユーザー実施）」と明記する。
- 実装の進み具合に合わせてチェックを更新する（セッションをまたいだ作業の再開時にも、どこまで完了したかを確認できるようにするため）。

### 5.6 リリース手順書
本番環境で変更を伴う作業がある場合のみ作成する。ただし、dbtのリリースのみの場合は、CDの決まった手順（4.5）で行うため作成しない。dbt以外の本番作業（Snowflakeのユーザー・ロール・スキーマの作成、実データの取り込み等）がある場合は作成する。

| 章 | 内容 |
|---|---|
| 概要 | 何をリリースするか、実施タイミング、所要時間の目安 |
| 実施者の分担 | 手順ごとの実施者（Claude／ユーザー）とその理由 |
| 注意事項 | 実行する場所・シェル、手順書に無い作業が必要になった場合の扱い |
| 手順 | 番号付きの手順。手順ごとにコマンド・操作と期待結果を書く |
| 失敗した場合の対応 | どこまで戻ってやり直せるか、Claudeに共有する際の注意 |
| 実施記録 | 実施日・手順・実施者・結果・備考 |

- 実施者の分担：本番環境への書き込み・変更を伴う手順と、実データに触れる手順はユーザーが実施する（`CLAUDE.md`のデータ取扱いの原則）。ローカル環境の確認や、本番環境への読み取り専用の接続確認はClaudeが実施してよい。
- 手順：環境の準備（仮想環境の有効化等）は最初の手順でまとめて行い、以降の手順は準備済みの前提で簡潔に書く。
- 受け入れテスト：手順の最後に、依頼者が実データで要件定義書の完了条件を満たしているかを確認する手順（結果の確認）を設ける。
- 手順書に無い作業が必要になった場合は、以下のとおり扱う。

| 手順書に無い作業 | 扱い |
|---|---|
| 本番環境に変更を伴う作業 | その場で中断する。手順書を修正してレビューし直すか、リリース自体を中止する |
| 本番環境に影響しない作業（ローカル環境の設定等） | 実施してよい。何を行ったかを実施記録に残す |

- 失敗した場合の対応：エラーメッセージをClaudeに共有する前に、取引の内容等の実データが含まれていないかを確認し、含まれる場合は伏せる旨を書く。

## 6. Python実行環境
dbt等のPythonパッケージは、開発者全員・CI等のどの環境でも同じバージョンで動作するよう、以下のルールで管理する。

- Pythonパッケージは、リポジトリ直下の仮想環境`.venv/`にのみ導入する。PC全体のPython環境には導入しない。ただし、実行のたびに作り直される使い捨ての実行環境（GitHub ActionsのCI／CD等）では、仮想環境を作らずに`requirements.txt`から直接導入してよい（他の用途と混ざらず、バージョンは`requirements.txt`で固定されるため）。
- 直接利用するパッケージ（例：`dbt-core`・`dbt-snowflake`）は、リポジトリ直下の`requirements.txt`に`==`でバージョンを固定して記載し、Gitで管理する。依存パッケージ（直接利用するパッケージが内部で使うもの）までは固定しない。
- `.venv/`自体はGitで管理しない（`.gitignore`で除外済み）。
- パッケージを追加・更新する場合は、`requirements.txt`の変更を同じPRに含める。
- 環境の作成手順は以下のとおり。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

- 仮想環境の外ではdbtが導入されていないため、仮想環境を使わずに実行するとコマンドが見つからずに失敗する。ルールに反した実行は、この失敗で自然に検知される。
